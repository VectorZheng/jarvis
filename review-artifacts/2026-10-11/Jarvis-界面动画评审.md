# Jarvis 界面与动画评审

评审日期：2026-10-11。对象：D:\Jarvis\jarvis-app，启动入口为 8082，检查期间 8083 也曾提供同一应用。用户指定后端为 http://10.205.9.212:9301。

**结论**

当前版本已经有安静、克制的视觉方向，适合做一个随身助手。值得保留的是灰白配色、较轻的分隔线、主界面的单一输入入口，以及把多个任务一起理解的能力。但体验仍有明显演示原型痕迹：入口缺少解释，部分控件无法完成其承诺，会话不能保留，动画和内部协作过程占用了结果的位置。

我建议下一轮先修复可用性，再收敛信息，再打磨动效。苹果风格的目标应写成可验收的行为：点击有及时反馈；位置变化有连续性；内容可读；键盘不会挡住操作；返回后仍能接着做；系统辅助功能设置得到尊重。圆角、模糊、弹簧都只是辅助。

**证据范围**

- 在 Edge 的独立无界面浏览器中，以 393×852、375×667 两个移动端视口检查页面。截图记录位于本目录。
- 实际操作过：首页、换形象、麦克风入口、发送示例、结果卡片、跟进、今日、秘书团、成员详情、习惯、我的，以及切页后返回。
- 读取了 App.tsx、TalkScreen.tsx、BossSkinPicker.tsx、Drops.tsx、sseClient.ts、index.ts 等实现。
- 以下“实际观察”与“源码风险”分别标注。浏览器视口不能代替实体 iPhone，未验证原生键盘、触感、侧滑返回、实际帧率和耗电。
- 另一个助手仍在开发，本报告针对截图和源码检查时的版本；执行改动前应核对当前代码，避免覆盖新成果。

**一、先修复四个会直接影响使用的问题**

1. 换形象弹层内容被裁切【实际观察＋源码确认】

在 393×852 视口中，弹层约 420 px 高，内容约 717 px；375×667 下弹层约 347 px，内容仍约 717 px。底部的形象及相册入口无法完整看到。BossSkinPicker.tsx 以 Math.min(height * 0.52, 420) 限高，内容是普通 View，外层 overflow:hidden，没有滚动区。顶部还有拖动条，但没有相应手势实现。

建议：标题与完成按钮固定，选项区域独立滚动，适配底部安全区。先做能完整滚动和能明确关闭的版本；若保留拖动条，再提供可用的拖拽与取消行为。不要单纯把高度改成另一个固定数字。选中项只需勾选与轻微背景变化，不必再播长动画。

证据：[弹层截图](D:/Jarvis/review-artifacts/2026-10-11/03-skin-sheet-open.png)、[小屏截图](D:/Jarvis/review-artifacts/2026-10-11/13-small-screen-sheet.png)。源码：[BossSkinPicker.tsx](D:/Jarvis/jarvis-app/src/talk/BossSkinPicker.tsx:28)。

2. 切页返回后对话消失【实际观察＋源码确认】

发送示例并看到三个结果后，切到今日、秘书团等页面，再返回说话，主界面恢复初始状态。App.tsx 条件挂载 TalkScreen，TalkScreen 的 reducer 与输入等状态在组件内；卸载会丢失这部分状态。

建议：先把当前会话状态放到页面生命周期之外，保留消息、任务状态、结果、草稿及适当的阅读位置；不要让换标签页等于新建对话。会话正在运行时离页，是继续运行还是明确停止，必须有一致行为。下一步再决定持久化哪些内容。符合仓库要求的 Expo Router 迁移要单独规划，不能靠换导航组件自动解决状态问题。

源码：[App.tsx](D:/Jarvis/jarvis-app/App.tsx:134)、[TalkScreen.tsx](D:/Jarvis/jarvis-app/src/talk/TalkScreen.tsx:128)。

3. 输入区仍是演示状态【实际观察＋源码确认】

输入默认填入“今晚想练一下，顺便看看冰箱能做啥，这周钱紧”，小屏上显示不全，发送后仍留在输入框。用户第一次进入会误以为这是一条草稿或自己输入过的内容。

建议：默认空输入；示例放成两个或三个可点击建议。“帮我安排今晚”“看看今天待办”这类示例只在初始空态出现。发送后将请求作为用户消息显示，并清空输入；失败时提供重试或恢复草稿，避免丢内容。输入支持有限行数增长，超过上限内部滚动，不能把整个聊天区挤没。

4. 麦克风承诺了尚未实现的功能【实际观察＋源码确认】

点击麦克风只显示“按住说话下一版接入，先打字”，并非录音。它处于最常用的输入位置，用户很容易把它当成有效语音入口。

建议：当前迭代暂时隐藏，或清楚地说明不可用；真正接入后才给出录音、取消、结束、权限拒绝等状态。主界面不要依赖点击后才知道不可用的功能。

**二、首页需要更有用，但不要变成仪表盘**

首页截图中，大圆球颜色很淡，直径约 200 px，舞台占 340 px；一条轮换短句之后，是大量留白和底部输入。它很安静，但缺少“我现在能做什么”的线索。圆球还承担换形象入口，可点击性不容易发现。

我会保留助手的视觉身份，但建议缩小首页标识，使用一句实用的欢迎语，例如“有什么想让我帮你处理？”下方放两三个真实支持的建议。装饰短句可以作为轻量个性设置，首屏优先呈现可做的事。

初始界面不必同时展示日程、天气、健康、花销、专才列表。复杂能力留在对话里。用户说完一句话，先知道助手已经接到，然后看到简洁结果。

如果坚持保留大圆球，应限于初始空态，并控制对比度，让它看起来是有意设计的实体。键盘展开、流式响应、结果出现时，都转换成小型状态标识；不能在结果结束后突然恢复大舞台，把已出现的内容推开。

证据：[首页](D:/Jarvis/review-artifacts/2026-10-11/01-home.png)、[跟进状态](D:/Jarvis/review-artifacts/2026-10-11/07-follow.png)。

**三、结果应围绕下一步行动呈现**

这次示例同时涉及运动、饮食和预算。三个卡片反复出现“头头”“我帮你定了”“用户任务标题”及专才说明，读起来像观看角色工作，而不是得到一份可用安排。跟进状态下，大圆与另一个圆/轮廓发生重叠和裁切，结果卡片被挤到更低位置。

建议改成“一个简要总答复＋任务项”，例如：

> 今晚先轻量活动 15 分钟，晚饭用现有食材，尽量不额外花钱。
>
> 运动：15 分钟低强度活动
>
> 晚饭：根据你确认的现有食材安排
>
> 预算：先按不新增开销来计划

这是信息结构示例，不是应当硬编码的个性化结论；实际建议必须来自真实请求、用户提供的信息和后端结果。

每个任务提供少量必要动作：调整、保存；执行动作只有能力真实存在时才出现。详细推理和角色协作放到“查看详情”。没有把任务写入日历，就不要说“已经安排好了”；只是生成建议，就说“我建议这样安排”。

跟进提示点击后应立即打开可见的详情弹层，或者展开紧邻提示的位置。当前面板插在更低的滚动区域，用户点击时很难立即感知发生了什么。

**四、把内部术语从主要路径收起来**

界面出现“头头、会商、会议纪要、否决、注册表、二期、演示种子、旧版今日”等文字。保留“头头”作为可选昵称没有问题，但多个术语叠加，会让产品像一个多智能体实验台。

建议保留一名用户面对的助手。背后的专才仍可协作，主要界面只呈现结果和必要确认。文案可以这样调整：

| 当前表达 | 建议表达 | 条件 |
| --- | --- | --- |
| 会商中 | 正在整理你的安排 | 真实请求正在处理 |
| 会议纪要 | 查看详情 | 用户确实需要阅读更多过程 |
| 否决 | 建议调整 | 给出简短原因，不把冲突演成主角 |
| 头头结论 | 给你的建议 | 属于建议时使用 |
| 跟进中 | 具体描述正在做的事 | 例如等待确认，而不是无期限状态 |
| 二期/下一版 | 暂时不展示入口 | 尚未实现的能力 |
| 旧版今日 | 从产品入口移除 | 作为开发入口保留也应明确区隔 |
| 演示种子/注册表 | 演示内容/能力设置 | 优先移到开发区域 |

这些表达是我的设计建议，不是 Apple 规定的用语。

**五、导航与其他页面**

当前主入口非常简洁，进入旧区域后又出现说话、今日、秘书团、习惯、我的五个标签，前后像两套产品。

建议优先维持两到三个稳定目的地：助手、记录、我的；只有今日能展示真实待办和日程时，才值得作为主要入口。秘书团和习惯可归入我的/助手设置，后台协作不必一直占据主导航。

今日：当前更像睡眠时长、可用时间、冰箱食材的演示控制台。正式页面应先展示今天的实际事项；影响建议的个人信息以编辑入口展开。没有数据时给出明确空态，不伪造丰富内容。

秘书团：分组列表和视觉秩序相对完整，可以保留作为次级页面。未上线角色、“二期”标签及开发说明不必直接暴露给普通用户。

习惯：无条目时同时出现“还没学到习惯”和“点一条进入”，两句互相矛盾。空态应说明如何形成习惯，例如“你确认过的偏好会显示在这里”，且说明必须符合实际产品行为。不要暗示用户无法控制的持续记录。

我的：账户、同步等尚不可用的入口先收起。优先提供真实可用的外观、形象、隐私/数据、辅助功能、反馈和版本信息。形象设置更适合从这里进入，不必让首页圆球承担隐藏入口。

**六、动画要减少等待、保留连续性**

实际浏览说明页面有状态切换和渐变；以下延迟、帧循环、滚动行为由源码确认，不等于实体 iPhone 上已经测出掉帧。

1. 请求先启动，视觉反馈同时发生。

TalkScreen.send() 在发起请求前固定等待 900 ms；sseClient 又传 pace_ms:900，文字显示还以每 30 ms 两个字推进，并在部分段落后停顿 700/900 ms。多层节奏可能把已经拿到的结果继续扣住。不要把这些数字相加成实际总延迟，因为它们可能部分重叠，但应逐层拆清楚。

建议立即请求，保留轻量“正在处理”状态。如果服务端已经流式输出，客户端避免再建一套拖慢内容的打字机。首段要尽快读到；取消应能停止已启动的流，也应取消尚未启动的定时任务。这次没有完成立即停止测试，执行助手需要验证“发送后立刻停止”不会在 900 ms 后重新启动请求。

2. 页面布局变化应协调。

舞台在不同状态间切换为约 340/88 px 等高度，圆球内部运动并不代表整个布局连续。建议同一布局里从较大标识收敛为小状态标识，避免结果出来再恢复大面积装饰。新结果出现时只做一次克制过渡。

3. 不要争夺滚动控制。

运行时 onContentSizeChange 调 scrollToEnd({animated:true})，打字机持续增加内容时可能反复驱动滚动；完成或停止后又延迟滚到顶部。建议只有用户接近底部才跟随，用户上滑阅读就暂停自动跟随，必要时显示“有新内容”按钮。完成后保留当前阅读位置。

4. 弹层反馈与内容操作应统一。

打开与关闭可使用轻微、快速收敛的弹簧。已有弹簧参数不证明手感符合 iPhone，应结合弹层大小、手势和真实设备调试。拖拽要跟随手指；中途取消要能连续返回。弹层标题和关闭按钮不要一起漂移得难以点击。

5. 长时间闲置动画应检查预算。

Drops.tsx 每帧执行 requestAnimationFrame、物理计算及 React setTick；减少动态效果模式下仍能进入这条循环。当前只看到 stopped 状态专门结束循环。建议动画稳定后停止，应用后台时暂停，减少动态效果时采用静态状态/淡化。必要时评估适配当前 SDK 的动画方案，让持续动画不依赖每帧 React 重渲染。不要未经实测就宣称“迁移后 120 FPS”。

我建议的初始调参范围如下，属于试验起点，不是系统标准：

| 场景 | 建议起点 | 验收重点 |
| --- | --- | --- |
| 按下按钮 | 约 80–120 ms 的轻微反馈 | 反馈立即出现；不等待动画完再执行 |
| 标识状态改变 | 约 180–260 ms | 尺寸/位置/透明度协调，无双圆残影 |
| 结果出现 | 约 180–240 ms，一次即可 | 可立即阅读，无逐句强制停顿 |
| 弹层呈现/关闭 | 约 250–350 ms，轻微弹簧 | 可打断、关闭可靠、滚动正常 |
| 减少动态效果 | 静态替换或很短的淡化 | 无持续呼吸、大位移或强制平滑滚动 |

**七、影响原生感的细节**

- 麦克风视觉框为 28×28，发送为 30×30，未看到额外命中区域。建议点击区域至少 44×44 逻辑单位，图标可以保持精巧；需要验证区域不会与相邻输入操作重叠。
- 未在已检查代码中找到完整键盘避让处理。实体 iPhone 上验证输入框始终在键盘上方、长输入可读、发送可点、关闭键盘后布局稳定。
- 当前固定浅色主题，StatusBar 为 dark。统一语义颜色后再增加随系统深浅色，暗色下不要简单反转所有颜色或照搬模糊强度。
- Windows/浏览器文字效果不代表 iOS 系统字体。设备上检查中文正文、标题层级和较大文字设置；不要靠大量不同字号、字重模拟精致。
- 次要灰色文字及淡圆球应验证对比度，不能为了轻盈让状态不可辨认。
- 形象是装饰时避免形成无意义的 VoiceOver 焦点；发送、停止、关闭、任务动作提供准确标签。运行中状态变化需要被读屏理解。
- 已有 reduce motion hook，但打字机、自动滚动、短句切换等尚未全面统一。所有装饰性动画都应接入同一策略。
- 触感只有在真实支持的操作中作为补充；网页预览不能验证触感，不必给每张卡片都加震动。

**八、一个独立的网页加载问题**

检查时 /canvaskit.wasm 返回 HTTP 200，却是 text/html，开头为 <!DOCTYPE html>，运行时 WebAssembly.instantiate 报错 expected magic word 00 61 73 6d, found 3c 21 44 4f。index.ts 通过 LoadSkiaWeb({ locateFile: f => '/' + f }) 加载后进入 fallback。

建议核查 web 静态资源路径。如果当前界面不再使用 Skia，应先确认全项目实际使用情况，再决定是否移除过时初始化；如果仍使用则正确提供 wasm 文件。当前圆球由 React Native View/渐变绘制，不能把它很淡或重叠直接归因于这个 wasm 错误。

**九、建议实施顺序与验收**

第一轮：修复弹层可达性、明确关闭、会话保留、默认空输入/发送清空、不可用麦克风、停止与延迟任务、wasm 问题。先不做大规模视觉重构。

第二轮：缩减结果页舞台，收敛结果卡片，修复跟进入口，删除用户路径上的内部术语和开发入口，统一导航与空态。

第三轮：处理重复延迟、滚动跟随、布局动画、闲置帧循环、命中区域、主题与辅助功能。

最后在实体 iPhone 验证：输入键盘、长输入、快速发送/停止、流式失败与重试、弹层滚动/拖动、切页返回、前后台、减少动态效果、深色、较大文字和读屏。浏览器验证 375×667 与 393×852 下内容无裁切；错误控制台不再出现 wasm 报错。展示实际完成的验证，不把未测试项写成通过。
